# Полное техническое описание АИС «ИСБ ГСМ»

**Редакция:** 2.0 (целевое техническое описание)  
**Дата:** 17.07.2026  
**Статус:** рабочий проектный документ; заменяет описание от 25.06.2026 после утверждения открытых решений из раздела 16.  
**Система:** АИС ведения химмотологических карт, нормирования ГСМ и индивидуальных карт.

---

## 1. Назначение системы

АИС «ИСБ ГСМ» предназначена для ведения справочников техники и ГСМ, разработки и согласования химмотологических карт (ХК), фиксации их версий, формирования индивидуальных карт (ИК), контроля сроков действия нормативных документов, ведения задач, уведомлений, аудита и отчётности.

Система работает с нормативной структурой техники:

```text
Комплекс
  -> Изделие
      -> Агрегат
          -> Узел
              -> Сборочная единица
```

Нормативная структура ХК повторяет уровни нормирования, начиная с узла:

```text
ХК комплекса
  -> ХК изделия
      -> ХК агрегата
          -> ХК узла
              -> Строки ХК: сборочные единицы, нормы, ГСМ
```

Сборочная единица не является самостоятельным объектом нормирования и не имеет собственной ХК.

## 2. Границы предметной области

### 2.1. Технические объекты

| Уровень | Доменная сущность | Назначение |
|---|---|---|
| 1 | `Complex` | Комплекс; объединяет изделия, является объектом навигации, классификации и верхнего уровня нормирования |
| 2 | `EquipmentModel` | Изделие/модель техники; входит в комплекс, состоит из агрегатов |
| 3 | `Aggregate` | Агрегат; самостоятельный объект справочника, состоит из узлов |
| 4 | `Node` | Узел; базовый объект нормирования, состоит из сборочных единиц на уровне строк ХК |
| 5 | `AssemblyUnit` | Сборочная единица; строка табличной части ХК узла, не имеет ХК |

`EquipmentInstance` — конкретный физический экземпляр изделия. Он связан с `EquipmentModel` и нужен для формирования и хранения ИК; не является отдельным уровнем ХК.

### 2.2. Два вида состава

В системе строго разделяются следующие понятия.

| Вид | Сущности | Вопрос, на который отвечает |
|---|---|---|
| Конструктивный состав техники | `ComplexComposition`, `ProductComposition`, `AggregateComposition` | Из каких объектов состоит техника и в каком количестве |
| Нормативный состав ХК | `HKCardComponent` | Какие конкретные утверждённые версии дочерних ХК включены в конкретную родительскую ХК |

Пример: конструктивный состав говорит «изделие содержит два агрегата А и один агрегат Б», а нормативный состав ХК изделия говорит «в ХК изделия v0726 включены ХК агрегата А v0626 и ХК агрегата Б v0726».

Нельзя хранить `HKCardId` в строках конструктивного состава как замену `HKCardComponent`. Новая версия дочерней ХК не должна изменять утверждённую родительскую ХК задним числом.

## 3. Технологический стек

| Направление | Технология |
|---|---|
| Backend API | ASP.NET Core Web API (.NET), REST, Swagger |
| Web UI | ASP.NET Core Razor Pages + Blazor Server для интерактивных фрагментов |
| ORM | Entity Framework Core + Npgsql |
| БД | PostgreSQL |
| Аутентификация | ASP.NET Core Identity, cookie authentication, policy-based authorization |
| Отчёты | QuestPDF (PDF/A4), ClosedXML (XLSX) |
| Развёртывание | On-premise; Docker Compose, IIS или bare metal |

Все идентификаторы предметных сущностей — `Guid` (UUID v4). Все даты и время в БД хранятся в UTC. Новый прикладной код получает время через `TimeProvider` из DI.

## 5. Конструктивные составы

### 5.1. Состав комплекса

```text
Complex
  -> ComplexComposition (версия состава)
      -> ComplexCompositionItem
          -> EquipmentModel
          -> Quantity
```

`ComplexComposition` описывает, какие изделия и в каком количестве входят в комплекс.

### 5.2. Состав изделия

```text
EquipmentModel
  -> ProductComposition (версия состава)
      -> ProductCompositionPart (логическая группа, опционально)
          -> ProductCompositionAggregate
              -> Aggregate
              -> Quantity
```

`ProductCompositionPart` используется для конструктивной группировки агрегатов, например «Силовая установка», «Трансмиссия» или «Система управления». Часть не является самостоятельным объектом нормирования.

### 5.3. Состав агрегата

```text
Aggregate
  -> AggregateComposition (версия состава)
      -> AggregateCompositionNode
          -> Node
          -> Quantity
```

### 5.4. Статусы составов

Для `ComplexComposition`, `ProductComposition` и `AggregateComposition` применяется единый enum:

```csharp
public enum ProductCompositionStatus
{
    Draft = 1,
    OnReview = 2,
    Approved = 3,
    Archived = 4
}
```

Переходы:

```text
Draft -> OnReview -> Approved -> Archived
             -> Draft
```

- Создание всегда формирует `Draft`.
- Редактирование частей, строк, количества и реквизитов допустимо только в `Draft`.
- `OnReview`, `Approved` и `Archived` доступны только для чтения.
- При утверждении нового состава прежний действующий утверждённый состав того же родителя архивируется в одной транзакции.
- У одного объекта одновременно может быть только один действующий утверждённый состав.
- `IsActive` — технический признак текущего утверждённого состава, не источник статуса и не поле ввода UI.
- Пустой черновик допустим, но отправить на проверку или утвердить пустой состав нельзя.

### 5.5. Ограничения состава

| Таблица | Уникальность | Правило |
|---|---|---|
| `AggregateCompositionNode` | `AggregateCompositionId + NodeId` | `Quantity > 0` |
| `ProductCompositionAggregate` | `ProductCompositionPartId + AggregateId` | `Quantity > 0` |
| `ComplexCompositionItem` | `ComplexCompositionId + EquipmentModelId` | `Quantity > 0` |

Все ограничения дублируются в PostgreSQL: unique indexes, FK и check constraints. Проверка только в UI недопустима.

### 5.6. Историческая миграция

До введения агрегата текущая модель `ProductCompositionNode` связывала изделие и узел напрямую. Её перенос выполняется двумя фазами:

1. Добавить новые таблицы без удаления старых записей.
2. В административном сценарии распределить старые узлы по созданным/выбранным агрегатам, создать новый состав изделия и сохранить старый как исторический.

Старые ИК и старые составы не переписываются. Прямые связи `ProductCompositionNode` удаляются только отдельной миграцией после подтверждения завершения переноса.

## 6. Химмотологические карты

### 6.1. Уровни ХК

Вводится уровень объекта карты:

```csharp
public enum HKObjectLevel
{
    Complex = 1,
    EquipmentModel = 2,
    Aggregate = 3,
    Node = 4
}
```

`HKCard` содержит ровно один нормативный объект:

```text
ObjectLevel = Complex        -> заполнен ComplexId
ObjectLevel = EquipmentModel -> заполнен EquipmentModelId
ObjectLevel = Aggregate      -> заполнен AggregateId
ObjectLevel = Node           -> заполнен NodeId
```

На уровне PostgreSQL должен действовать `CHECK`, запрещающий ноль или несколько одновременно заполненных идентификаторов нормативного объекта.

### 6.2. Назначение карт по уровням

| Уровень | Тип ХК | Содержимое |
|---|---|---|
| Узел | Базовая ХК | Редактируемые `HKCardItem`, сборочные единицы, нормы, марки ГСМ |
| Агрегат | Агрегирующая ХК | Выбранные утверждённые ХК узлов; расчётные read-only строки |
| Изделие | Агрегирующая ХК | Выбранные утверждённые ХК агрегатов; расчётные read-only строки |
| Комплекс | Агрегирующая ХК | Выбранные утверждённые ХК изделий; расчётные read-only строки |

Ручные `HKCardItem` разрешены только в ХК узла. В агрегирующих ХК ручное добавление строк ГСМ первого этапа запрещено.

### 6.3. Нормативный состав ХК

```csharp
public class HKCardComponent
{
    public Guid Id { get; set; }
    public Guid ParentHKCardId { get; set; }
    public Guid ChildHKCardId { get; set; }
    public int SortOrder { get; set; }
    public DateTime AddedAt { get; set; }
    public string AddedByUserId { get; set; } = null!;
}
```

Ограничения:

- уникальность `ParentHKCardId + ChildHKCardId`;
- дочерняя ХК имеет статус `Approved` и действительна на дату выбора;
- ХК агрегата включает только ХК узлов из утверждённого состава агрегата;
- ХК изделия включает только ХК агрегатов из утверждённого состава изделия;
- ХК комплекса включает только ХК изделий из утверждённого состава комплекса;
- прямые и косвенные циклы состава запрещены;
- изменение компонентов запрещено после отправки родительской карты на проверку;
- архивирование дочерней ХК не удаляет её из истории утверждённой родительской ХК.

Для воспроизводимости в компоненте либо отдельной snapshot-таблице фиксируются отображаемые код, версия и дата утверждения дочерней ХК на момент включения.

### 6.4. Статусы ХК

```csharp
public enum HKCardStatus
{
    Draft,
    OnReview,
    RevisionRequired,
    Approved,
    Archived,
    Deleted
}
```

Целевые переходы:

```text
Draft -> OnReview -> Approved -> Archived
             |          ^
             v          |
      RevisionRequired -+

Draft / OnReview / RevisionRequired -> Deleted  // только отказная версия по разрешению
```

- `Draft` — редактируемая черновая карта.
- `OnReview` — отправлена на проверку, содержание блокируется.
- `RevisionRequired` — возвращена на доработку; комментарий опционален.
- `Approved` — утверждённая нормативная карта.
- `Archived` — историческая карта, не используется для новых ИК и новых агрегирующих ХК.
- `Deleted` — отказная/закрытая версия документооборота, не физическое удаление.

### 6.5. Пустая отказная ХК

Пустая ХК создаётся только для документооборотного сценария отказа. Она может не содержать обычные обязательные нормативные данные и строки, но обязана иметь:

- объект или идентифицируемое основание, если объект ещё не определён;
- автора;
- дату создания;
- причину отказа/закрытия;
- журнал статусов.

Пустая карта не может стать `Approved`, использоваться в ИК, включаться в агрегирующие ХК или попадать в расчёты. Для обычной ХК обязательные поля и строки валидируются при отправке на проверку/утверждении, а не при самом создании Draft.

### 6.6. Версии ХК

Версия отображается в формате `vMMYY`. Если для одного объекта возможны несколько выпусков в одном месяце, внутренний `RevisionNumber` обязателен; отображаемая версия должна стать `vMMYY.N` либо правила выпуска должны запрещать второй выпуск в месяц. Это решение должно быть утверждено до миграции.

Каждая новая редакция утверждённой ХК создаётся как новая запись и ссылается на заменяемую карту через `SupersedesHKCardId`. Предыдущая версия сохраняется для просмотра, отчётов, ИК и аудита.

В карточке и просмотре ХК выводится список версий объекта: версия, статус, дата утверждения, срок действия, автор и ссылка перехода.

### 6.7. Срок действия

- `EffectiveDate` — дата начала действия.
- `ExpirationDate` — дата окончания действия.
- При `ExpirationDate < EffectiveDate` сохранение отклоняется.
- По окончании срока утверждённая ХК автоматически архивируется фоновой задачей.
- При выборе действующей ХК учитываются одновременно статус `Approved`, дата начала и дата окончания.

### 6.8. Код ХК

Код формируется сервером. Базовый формат:

```text
ХК-{код_нормативного_объекта}-{год}
```

Для исключения коллизий при нескольких картах допускается серверный числовой суффикс. Код и версия не вводятся пользователем как произвольный текст.

## 7. Карточка ХК

### 7.1. Реквизиты основания

Над полями номера ХК и объекта отображаются слева направо:

```text
Организация | ФИО отправителя | Дата поступления | Реквизиты |
Номер письма: Входящий | Исходящий | Род войск | PDF-скан
```

Поля:

| Поле | Тип | Назначение |
|---|---|---|
| `RequestOrganization` | string | Организация, направившая обращение |
| `RequestSenderFullName` | string | ФИО отправителя/подписанта |
| `RequestReceivedDate` | DateTime? UTC | Дата поступления письма |
| `RequestDetails` | string | Реквизиты/основание |
| `IncomingLetterNumber` | string | Входящий номер |
| `OutgoingLetterNumber` | string | Исходящий номер |
| `MilitaryBranches` | связь со справочником/текст для основания | Род(а) войск |

Эти поля доступны в поиске, фильтрах, PDF/XLSX, карточке просмотра и аудите значимых изменений.

### 7.2. Рода войск

Использовать справочник `MilitaryBranch`.

- У ХК изделия — связь many-to-many `HKCardMilitaryBranch`; можно выбрать несколько значений.
- Для реквизитов входящего письма допускается отдельный текст или выбор из того же справочника согласно утверждённой форме делопроизводства.
- Не хранить множественный выбор строкой с разделителями.

### 7.3. PDF-вложение

К ХК прикрепляется один PDF-скан исходной химмотологической карты.

```csharp
public class HKCardAttachment
{
    public Guid Id { get; set; }
    public Guid HKCardId { get; set; }
    public string OriginalFileName { get; set; } = null!;
    public string StorageKey { get; set; } = null!;
    public string ContentType { get; set; } = "application/pdf";
    public long SizeBytes { get; set; }
    public string UploadedByUserId { get; set; } = null!;
    public DateTime UploadedAt { get; set; }
}
```

Требования:

- допустим только `application/pdf`, с проверкой сигнатуры файла, а не только расширения;
- ограничение размера задаётся конфигурацией;
- файл выдаётся только пользователю, имеющему право просмотра соответствующей ХК;
- предпросмотр открывается в панели либо новом окне браузера без принудительного скачивания;
- замена/удаление вложения после утверждения создаёт новую версию ХК либо запрещается;
- путь файловой системы и внутренний `StorageKey` не раскрываются UI.

### 7.4. Быстрое добавление справочников

В редакторе ХК узла searchable select для узла, сборочной единицы и ГСМ содержит действие `Добавить новый`.

| Предложение | Поля |
|---|---|
| Узел | Код, наименование, описание |
| Сборочная единица | Код, наименование, описание |
| ГСМ | Наименование, ГОСТ, тип |

Быстрое добавление не должно сразу публиковать запись в общий справочник. Используется сущность предложения, например `ReferenceProposal`, с состояниями `Pending`, `Accepted`, `Rejected`.

- Предложение доступно только в текущей Draft ХК.
- При утверждении ХК уполномоченный пользователь подтверждает публикацию предложений или отклоняет ХК/предложения.
- После `Accepted` создаётся/активируется нормальная запись справочника и ссылки Draft ХК заменяются на итоговый `Guid`.
- Код и наименование проверяются на дубли до публикации.

### 7.5. Строки ХК

`HKCardItem` содержит сборочную единицу, количество, норму, единицу измерения, периодичность, примечание и порядок. `HKCardItemMaterial` связывает строку с ГСМ и категорией:

```text
Main | Duplicate | Reserve | Foreign
```

При выборе ГСМ в строке выводить:

```text
Наименование — ГОСТ
```

ГОСТ также выводится в просмотре ХК, PDF, XLSX и ИК. Марки выбираются из активного справочника; произвольный ввод марки запрещён.

### 7.6. Pop-up и списки выбора

Всплывающие списки редактора строк ХК должны:

- отображаться выше контейнеров и соседних панелей;
- не обрезаться `overflow` контейнера;
- автоматически открываться вверх при недостатке места снизу;
- закрываться по выбору, клику вне, `Escape`, переключению строки;
- поддерживать клавиатурную навигацию и корректный focus;
- не выходить за границы viewport.

Для этого использовать единый переиспользуемый Blazor-компонент select/popover с расчётом размещения, а не отдельные CSS-исправления для каждой колонки.

## 8. Индивидуальные карты

### 8.1. Назначение

ИК формируется для конкретного `EquipmentInstance`, ссылается на исходные утверждённые ХК, состав техники и применённые коэффициенты. ИК — исторический снимок: изменение актуальных справочников, состава или ХК не изменяет ранее сформированную ИК.

### 8.2. Модель

```text
IndividualCard
  -> EquipmentInstance
  -> ProductCompositionId (версия использованного состава)
  -> HKCard / HKCardItem references or snapshots
  -> IndividualCardItem
  -> AppliedCoefficient snapshots
```

После введения ХК агрегата алгоритм ИК должен использовать утверждённую нормативную цепочку:

```text
Экземпляр изделия
  -> действующий утверждённый состав изделия
  -> утверждённая ХК изделия
  -> ХК агрегатов
  -> ХК узлов
```

Точный способ выдачи ИК (одна агрегированная ИК на экземпляр или отдельные связанные карточки по агрегатам/узлам) должен быть закреплён отдельным решением до реализации.

### 8.3. Правила

- Для расчёта выбираются только утверждённые и действующие составы/ХК.
- Нельзя использовать fallback «последний созданный состав».
- Ручное изменение нормативных строк после генерации запрещено; допускается изменение заметки и формирование новой версии ИК.
- Коэффициенты сохраняются снимком: название, значение, условия, тип и идентификатор исходного коэффициента.
- Повторная генерация формирует новую версию ИК, а не перезаписывает историческую.

### 8.4. UI ИК

Раздел должен включать реестр, фильтр по экземпляру/модели/филиалу/дате, выбор коэффициентов, генерацию, просмотр расчёта и источников норм, историю версий, PDF и XLSX.

Пока ХК агрегата не реализована, генерация по новой структуре блокируется контролируемым сообщением. Нельзя рассчитывать норму по неполной или неверно интерпретированной цепочке.

## 9. Роли и разрешения

### 9.1. Базовые роли

| Роль | Назначение |
|---|---|
| `SystemAdmin` | Полный доступ, настройка пользователей, ролей и системных параметров |
| `NormAdmin` | Нормативное администрирование: согласование/утверждение ХК и составов, справочники в пределах полномочий |
| `Operator` | Работа с ХК узла и собственными черновиками; остальные нормативные уровни по умолчанию — просмотр |
| `HeadOfDepartment` | Просмотр, контроль, задачи подразделения и отчётность в пределах филиала/подразделения |
| `Guest` | Только просмотр разрешённых данных; без ввода, изменения, удаления, генерации ИК и выполнения задач |

Текущая устаревшая роль `Viewer`, если присутствует, мигрируется в `Guest` либо сохраняется только как технический алиас на период миграции.

### 9.2. Точечные права

Базовая роль — шаблон. Пользователю могут быть добавлены разрешения-исключения, например Оператору разрешено создавать ХК изделия.

Примеры permissions:

```text
HK.View
HK.Node.Create / EditDraft / Submit
HK.Aggregate.Create / EditDraft / Submit
HK.EquipmentModel.Create / EditDraft / Submit
HK.Complex.Create / EditDraft / Submit
HK.Review / Approve / Archive
Reference.View / Edit
IndividualCard.Generate
Report.Export
Task.View / Complete / Assign
Audit.View
Users.Manage
```

Проверка разрешений выполняется policy-based authorization и на уровне сервисов. Скрытие кнопки в UI не является защитой.

### 9.3. Филиалы

Если пользователь не `SystemAdmin`, сервисы ограничивают чтение и изменение данными его `BranchId`. Переданный из UI `BranchId` не может расширять права пользователя. Межфилиальное использование ХК и справочников запрещено до отдельного утверждённого правила.

## 10. Справочники и реестры

### 10.1. Общие правила

Для справочников `Complex`, `EquipmentModel`, `Aggregate`, `Node`, `AssemblyUnit`, `GsmMaterial`, `MilitaryBranch`, типов техники и коэффициентов:

- поиск, фильтрация, сортировка и пагинация выполняются на сервере;
- read-only роли видят информационные таблицы/карточки без полей ввода и команд изменения;
- мягко удалённые записи не предлагаются для новых документов, но доступны для исторического просмотра;
- попытка удалить используемую в утверждённой ХК, ИК или составе запись отклоняется либо переводит её в архив.

### 10.2. ГСМ

`GsmMaterial`: `Id`, `Name`, `Type`, `Gost`, `Description`, `IsDeleted`, `DeletedAt`.

Фильтры: наименование, тип, ГОСТ, активность/архив. В таблице обязательно выводить ГОСТ.

### 10.3. Поиск

`SearchService` принимает `SearchQuery`:

```csharp
public class SearchQuery
{
    public string Text { get; set; } = string.Empty;
    public string? EntityType { get; set; }
    public DateTime? CreatedFrom { get; set; }
    public DateTime? CreatedTo { get; set; }
    public HKCardStatus? HKCardStatus { get; set; }
    public Guid? BranchId { get; set; }
    public string SortBy { get; set; } = "CreatedAt";
    public bool SortDescending { get; set; } = true;
    public int MaxResults { get; set; } = 50;
}
```

- Фильтр `EntityType` применяется до полнотекстового условия.
- `CreatedAt` и `ApprovedDate` сортируются SQL `ORDER BY`.
- `Title` и `EntityType` могут сортироваться в памяти только после серверного ограничения набора.
- Все реестры используют явные DTO-проекции, а не тяжёлые `Include` графов для списка.

## 11. Задачи и уведомления

### 11.1. Различие

| Объект | Смысл |
|---|---|
| `WorkTask` | Обязательное действие, назначенное конкретному пользователю или роли |
| `Notification` | Информационное событие; может не требовать действия |

### 11.2. Задачи

`WorkTask` должен поддерживать: заголовок, описание, тип, ссылку на сущность, инициатора, исполнителя, срок, приоритет, статус, дату выполнения, дату создания и филиал.

Источники автоматических задач:

- ХК/состав отправлены на проверку;
- ХК возвращена на доработку;
- утверждена новая дочерняя ХК, а родительская ХК требует пересмотра;
- истекает срок действия ХК;
- предложение нового справочного объекта ожидает решения;
- административная задача управления пользователями, если такой сценарий утверждён.

В sidebar у раздела «Задачи» показывается цифровой бейдж с точным количеством открытых задач текущего пользователя. Количество вычисляется сервером и обновляется после изменения задачи.

### 11.3. Уведомления и колокольчик

Колокольчик остаётся в topbar и показывает количество непрочитанных уведомлений. В выпадающем списке: тип, заголовок, дата, ссылка на объект/задачу, действие «прочитано».

Сроки ХК формируют уведомления за 90, 30 и 7 дней, а также в день истечения. Если назначен ответственный, за 30 и 7 дней создаётся задача на пересмотр; значения сроков должны быть конфигурационными.

Фоновая задача ежедневно:

1. Находит ХК с приближающейся `ExpirationDate`.
2. Не создаёт дубли уведомлений/задач.
3. Архивирует истёкшие Approved ХК.
4. Записывает аудит системного действия.

## 12. Аудит

`AuditLog` должен содержать:

```text
Id, EntityType, EntityId, EntityCode/Title snapshot, Action,
UserId (string Identity), BranchId, Details,
OldValues JSON, NewValues JSON, CreatedAt UTC, Source
```

Аудит записывается в том же `AppDbContext` до единственного `SaveChangesAsync` бизнес-операции. Не допускается успешное изменение нормативных данных без аудита.

Журнал аудита поддерживает фильтры по: пользователю, дате/периоду, сущности, коду/наименованию, действию, филиалу и тексту деталей; сортировку и серверную пагинацию.

Не записывать в аудит пароли, access token, содержимое PDF и иные секреты.

## 13. Управление пользователями

Раздел `Пользователи` доступен `SystemAdmin`.

Функции:

- создание пользователя;
- ФИО, должность, филиал, активность;
- назначение одной базовой роли;
- назначение точечных permissions;
- деактивация без удаления истории;
- смена/сброс пароля по политике безопасности;
- просмотр действующих ролей и исключений;
- аудит административных операций.

Пользователь с read-only правами видит только информацию, но не формы ввода. Любая операция проверяется на сервере.

## 14. Отчёты

### 14.1. PDF

QuestPDF генерирует PDF A4 ХК и ИК. В ХК включаются:

- реквизиты основания;
- объект, код, версия, статусы и сроки;
- история версий/ссылка на заменяемую карту при необходимости;
- строки сборочных единиц;
- ГСМ с ГОСТ;
- для агрегирующих ХК — источники каждой агрегированной строки;
- роды войск для ХК изделия;
- сведения о PDF-вложении, но не обязательное встраивание скана в отчёт.

### 14.2. XLSX

ClosedXML формирует экспорт с применёнными фильтрами. Крупные отчёты должны ограничиваться серверным лимитом или формироваться фоново; не загружать неограниченные entity-графы в Blazor circuit.

```css

```

Использовать стандартные классы:

```text
.panel, .panelHeader, .field, .btn, .btn.primary, .tag, .status,

```

Layout: sidebar 290px, topbar 64px, desktop grid `290px 1fr`, gap 14px, breakpoints 1120px и 560px. Hover: `translateY(-1px)`. Focus: border + `box-shadow: 0 0 0 3px rgba(79,140,255,.12)`.

### 15.2. Read-only режим

При отсутствии права изменения UI:

- показывает таблицы, карточки, статусы и ссылки;
- не отображает инпуты, select, textarea, кнопки создания/удаления/изменения;
- не полагается только на скрытие элементов: сервисная проверка остаётся обязательной.

### 15.3. Формы

Поля создаются через `.field`; нельзя заменять UI-kit бессистемными inline-style. Длинные таблицы используют серверную пагинацию, search/filter и устойчивую горизонтальную прокрутку на малых экранах.

## 16. Открытые решения для утверждения

Следующие вопросы нельзя закрывать самостоятельным кодовым решением. До утверждения они отмечаются в backlog/ADR.

1. **Версия ХК:** допускаются ли несколько выпусков одной ХК в месяц? Если да, принять `vMMYY.N` и `RevisionNumber`.
2. **Составы и будущая дата:** если новый состав утверждён сегодня, но действует в будущем, допустимо ли одновременно иметь старый `Approved/IsActive` и новый `Approved/not active`? Рекомендуемое правило — да.
3. **ИК:** одна агрегированная ИК на экземпляр изделия или отдельные ИК по агрегатам/узлам, объединённые в пакет? Это определяет модель и UI расчёта.
4. **Рода войск:** использовать общий справочник для реквизита входящего письма и назначения ХК изделия либо это два разных классификатора?
5. **Пустая отказная ХК:** обязателен ли объект нормирования при её создании, или достаточно реквизитов входящего письма и причины?
6. **Предложения справочников:** кто утверждает предложения, созданные из ХК: `NormAdmin`, отдельная роль или утверждение ХК автоматически публикует их?
7. **Хранение PDF:** файловая система, S3-совместимое внутреннее хранилище или PostgreSQL large object; максимальный размер и срок хранения.
8. **Межфилиальные данные:** допускаются ли общие справочники техники и ГСМ при раздельных ХК филиалов, либо все объекты должны быть ограничены `BranchId`?
9. **Комплектация:** допускается ли один агрегат в нескольких частях одного изделия и один узел в нескольких агрегатах. Базовое правило: дубль в одном составе запрещён, в разных типовых составах допустим.
10. **Уведомления:** какие события кроме сроков ХК обязательны для колокольчика, и могут ли пользователи отключать информационные уведомления.

## 17. Порядок реализации

1. **Базовая модель и составы:** `Aggregate`, состав агрегата, адаптация состава изделия, состав комплекса, миграция legacy-узлов.
2. **Нормативная иерархия:** `HKObjectLevel`, ХК агрегата/изделия/комплекса, `HKCardComponent`, агрегирование и версии.
3. **Жизненный цикл ХК:** отказные карты, корректные Draft-валидации, сроки, архивирование, история версий.
4. **Карточка ХК:** новые реквизиты, роды войск, PDF, предложения справочников, ГОСТ, popover-компонент.
5. **Права:** Guest, ограничение Operator, permission-модель, UI управления пользователями.
6. **ИК:** новая нормативная цепочка, снимки коэффициентов, UI, PDF/XLSX.
7. **Задачи, уведомления, аудит:** полный workflow, колокольчик, бейдж, фоновые работы, аудит-фильтры.
8. **Поиск, реестры и отчёты:** полный `SearchQuery`, фильтрация справочников, производительность экспортов.

Каждый блок выполняется отдельными PR с миграцией, тестами, code review и проверкой UI в светлой/тёмной теме на desktop/mobile.

## 18. Критерии качества

- Нормативные документы воспроизводимы: новая версия состава, ХК, ГСМ или коэффициента не меняет исторические ХК/ИК.
- Все критичные правила проверяются в сервисах и PostgreSQL, а не только в UI.
- Действия пользователя и системные фоновые действия аудируются.
- Роли и permissions проверяются на сервере и ограничиваются филиалом.
- Утверждённые карты и составы read-only.
- Архивные и удалённые данные не пропадают из истории, но не используются в новых расчётах.
- UI соответствует единому UI-kit и корректно работает при ограниченных размерах viewport.
- Миграции не уничтожают исторические данные и не «угадывают» структуру техники без подтверждения пользователя.
