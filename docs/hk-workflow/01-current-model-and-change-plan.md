## 3. Иерархия и термин «агрегат»

### 3.1. Что уже есть

Агрегат — **не новый термин**, а существующий самостоятельный уровень:

- сущность `Aggregate` (`Entities\Aggregate.cs`), `IsDeleted` — мягкое удаление;
- `HKCard.AggregateId` (`:28`) и `HKObjectLevel.Aggregate = 3`;
- собственные составы `AggregateComposition` → `AggregateCompositionNode` (узлы);
- место в конструктивных составах: `ProductCompositionAggregate` (агрегаты в составе изделия);
- справочник и страницы: `AggregatesReference.razor`;
- собственные права: `HKAggregateCreate`, `HKAggregateSubmit`, `HKAggregateEditDraft`.

Текущая лестница включений (`ValidateLevelChain:1196`) — ровно требуемая:
`комплекс → изделие`, `изделие → агрегат`, `агрегат → узел`.

### 3.2. Расхождения с требуемым

| Требование | Текущее поведение |
|---|---|
| Уровень выводится из верхних строк | Уровень — ввод пользователя; проверяется только при включении |
| Узел → агрегат **или** изделие, выбор пользователя | Для уровня `Node` включения дочерних ХК **запрещены** (`ValidateNodeRowsForReviewAsync`, `HKCardValidationService.cs:101`); узел — конечный уровень |
| Промежуточные уровни могут отсутствовать | Требуются: `EquipmentModel → Aggregate → Node` — только `Aggregate→Node` и `EquipmentModel→Aggregate`, прямого `EquipmentModel→Node` нет |
| Сборочная единица — конечная строка с нормами | Так и есть: `HKCardItem` ссылается на `AssemblyUnit` |
| Агрегат не существует вне содержащей структуры | Тесно связан: агрегат без изделия не пройдёт `ObjectExistsAsync`; включение проверяет членство в утверждённом составе |

Добавление уровня агрегата **не требуется** — он уже выражен в модели, и
противоречие операционное, а не структурное: меняется способ определения
уровня и допустимость пропуска уровней.

Объём изменений модели для нового процесса этим не исчерпывается и определяется
отдельно: раздел 6 перечисляет хранилище принятой структуры, раздел 4 — поле
названия, 2 — количество позиции. Каждое из них может потребовать
миграции; совокупный объём не определён этим PR.

### 3.3. Согласованные решения

- Автономная ХК не требует справочного объекта: идентичность определяется `Id`, а не ссылкой на `Aggregate`, `Node`, `EquipmentModel` или `Complex` и не совпадением названия.
- Одинаковое название не запрещает несколько карт с различными составами; автоматическое объединение не выполняется.
- Правило «одна активная ХК на справочный объект» к автономным картам не применяется. `EnsureNoActiveDuplicateAsync` и обработка `UX_HKCards_OneActivePer` пересматриваются в соответствующем PR.
- Версии не используются как обходной способ хранения самостоятельных карт с разными составами. Доработка одной карты и создание другого документа — разные операции.
- Уровень карты сохраняется как характеристика ХК и определяется по согласованным правилам верхних строк. Отмена справочной привязки не означает отмену уровня.
- Марки ГСМ продолжают выбираться из общего справочника.
- Снимок дочерней ХК внутри родителя исключается. Хранение собственной последней принятой структуры сохраняется: оно необходимо, чтобы при доработке карты оставались видны ранее принятые данные.
- Существующие таблицы и API включений не удаляются автоматически; их дальнейшую судьбу определить отдельно. ИК не является основанием продолжать использовать их в новом сценарии.
- Проверки циклов межкарточных включений новому сценарию не нужны. Собственное дерево должно исключать назначение позиции родителем самой себе или своему предку.
- Функциональная совместимость нового сценария ХК с ИК не является критерием приёмки. Существующий код ИК не переписывать и не удалять.

### 3.6. Решение по источнику номера автономной ХК (PR № 3)

Для автономной ХК средняя часть номера берётся **из введённого названия**, а не
из справочного кода. Формат: `ХК-{название объекта}-{год}`.

Отдельное поле кода объекта не требуется. Название — самостоятельное поле
`HKCard.Name`, вводится вручную, хранится раздельно от номера.

Последствия этого решения:

- справочный объект для создания автономной карты не нужен, и уровень остаётся
  неопределённым до вывода по структуре;
- год берётся из существующей инфраструктуры времени (`TimeProvider`), отдельная
  трактовка даты не вводится;
- механизм числового суффикса при совпадении базового номера сохранён;
- не вводятся: ежегодная последовательная нумерация, отдельный обязательный
  код объекта, транслитерация, подстановка справочного кода, временный
  `AUTONOMOUS-{Id}`.

## 4. Название и генерация номера

**Механизм существует** и описан в 1.3; исходный код объекта — `ResolveObjectCodeAsync:1382`.

Расхождение с требованием: номер и название занимают одно поле `Code`.
`GenerateCodeAsync:1290` требует `objectCode` — существующий объект нормирования,
которого в новом сценарии нет (см. решение 3.3). Значит механизм в нынешнем
виде неприменим, и это предмет пункта 3.5.2.

Чего не хватает: поля «название» в модели, способа формировать номер без объекта,
и определения, где показываются оба значения.

Формат `ХК-{код}-{год}` повторяет уже принятое в системе написание и в требованиях
не переопределён — менять его без отдельного решения оснований нет.

## 5. Проект двухэтапного согласования

### 5.1. Необходимые состояния и действия

Механизм представления двух этапов **не выбран** — это предмет пункта 3.5.3.
Ниже перечислено, какие состояния и действия нужны, без указания способа
хранения.

Неизменность `HKCardStatus` — ограничение **первого** PR, а не обязательное
правило последующих: если выбранное представление потребует расширения перечисления,
это отдельное решение.

Необходимо различать как минимум:

| Состояние | Смысл |
|---|---|
| Реквизиты не согласованы | заполняются реквизиты, основание и строки |
| Реквизиты на согласовании | реквизиты заблокированы, строки заполняются |
| Реквизиты приняты | позиции собственного дерева и конечные строки редактируются; отправка на согласование состава доступна при успешной валидации |
| Состав на согласовании | позиции дерева и конечные строки заблокированы |
| Состав возвращён | строки разблокированы на исправление |
| Состав принят | карта опубликована; доступна доработка с сохранением принятой структуры |

Сопоставление с текущими шестью статусами (`HKCardStatusTransitions.cs:7`)
пока не фиксируется: один статус не может различать «реквизиты приняты» и
«состав на согласовании», а это разные состояния с разными правами.

### 5.2. Разрешённые действия

| Состояние | Реквизиты и основание | Позиции дерева и конечные строки | Согласующий |
|---|---|---|---|
| Реквизиты не согласованы | правка | правка | — |
| Реквизиты на согласовании | **просмотр** | **заполнение первоначальным автором**; отправка на согласование состава ещё недоступна | принять / вернуть |
| Реквизиты приняты | просмотр | правка, отправка на согласование состава | — |
| Состав на согласовании | просмотр | **просмотр** | принять / вернуть |
| Состав возвращён | просмотр | правка, повторная отправка | — |
| Состав принят | просмотр | просмотр | начало доработки |

Возврат не удаляет строки, комментарий при нём не обязателен.

Доработка принятой карты — **правка той же карты**, а не обязательное создание
новой видимой ХК. Последняя принятая структура при этом остаётся видимой и
не подменяется рабочей. Внутреннее представление доработки (отдельные редакции,
снимки или работа в текущей карте с двумя наборами структур) техническим
решением не выбран — см. 5.4 и пункт 3.5.4.

Обязательные условия, уже обеспеченные кодом и сохраняемые:
отправка — права уровня (`CheckStatusChangePermissionAsync:2801`);
возврат — `HKReview` (`:2819`); утверждение — `HKApprove` (`:2814`);
NormAdmin должен быть назначен (`ChangeStatusAsync:1812`);
удаление — только в активных статусах (`CanDelete`, `HKCardStatusTransitions.cs:23`).

### 5.3. Роли

Согласующий — **конкретный пользователь**. Сейчас задача создаётся на роль
`NormAdmin` (`ApplyWorkflowTasksAsync:2357`), а `ReviewerId` пишется только при
утверждении (`:1829`). Требуется адресное назначение и фиксация назначенного
согласующего до начала этапа — иначе первый же NormAdmin в филиале станет
согласующим неявно.

### 5.4. Блокировки редактирования

Сейчас блокировка выводится из статуса в семи местах
(`HKCardService.cs:625, 987, 1070, 1567, 1588, 2871` и `AddComponentAsync`).
Одного признака «этап не начат» недостаточно: он не описывает возврат уже
начатого этапа. Полный набор правил:

| Ситуация | Реквизиты | Позиции дерева и конечные строки |
|---|---|---|
| До отправки на согласование | правка | правка |
| Этап реквизитов на рассмотрении | просмотр | **правка** |
| Реквизиты приняты, состав не отправлен | просмотр | правка |
| Состав на рассмотрении | просмотр | **просмотр** |
| Состав возвращён | просмотр | правка, повторная отправка |
| Состав принят | просмотр | просмотр опубликованной структуры |
| Доработка принятой карты | правка — с повторным прохождением этапа реквизитов | правка рабочей структуры — с повторным прохождением этапа состава |

Изменение обеих частей возвращает оба этапа. Замена PDF
(`SaveAttachmentAsync:625`) — также оба этапа с повторной проверкой строк.

Правила собственного дерева: позиция не может быть родителем самой себе или
своего предка (решение 3.3). Проверки циклов межкарточных включений
(`DetectCycleAsync:1251`, `HasCycleAsync:471`) новому сценарию не нужны.

### 5.5. Начало учёта срока

Согласован момент **начала обработки сроков**, а не автоматическая подстановка
одной даты вместо другой. Три величины различаются:

| Величина | Смысл | Текущее поле |
|---|---|---|
| Дата принятия реквизитов | момент, с которого карта учитывается фоновой обработкой сроков | нет отдельного поля |
| Начало действия карты | введённая пользователем дата вступления в силу | `EffectiveDate` |
| Окончание действия карты | введённая пользователем дата окончания | `ExpirationDate` |

Сейчас `ApprovedDate` и `EffectiveDate` заполняются одним переходом
(`:1826–1832`), а фоновая архивация (`HKCardExpirationService:228`) отсчитывает
от `ExpirationDate`. `EffectiveDate` и `ExpirationDate` имеют самостоятельный
смысл и подменять их датой согласования не следует.

Конкретное соответствие полей — предмет пункта 3.5.3 (модель согласований):
требуется определить, какое поле хранит дату принятия реквизитов и какое
условие включает карту в фоновую обработку. Состав и нормы на срок не влияют.

### 5.6. Техническая модель двух этапов (PR № 4)

Рабочие имена полей и перечислений зафиксированы здесь.

| Сущность / перечисление | Имя | Значения |
|---|---|---|
| Перечисление этапа | `HKApprovalStage` | `Details` = 1, `Composition` = 2 |
| Перечисление состояния этапа | `HKApprovalStageState` | `Draft` = 0, `OnReview` = 1, `RevisionRequired` = 2, `Approved` = 3 |
| Сущность | `HKCardApproval` | одна запись на пару «карта + этап» |
| Состояние этапа | `HKCardApproval.State` | `HKApprovalStageState` |
| Назначенный согласующий | `HKCardApproval.AssignedApproverUserId` | строка, ключ Identity |
| Дата принятия этапа | `HKCardApproval.ApprovedAtUtc` | заполняется один раз |
| Версия строки | `HKCardApproval.RowVersion` | `xmin` PostgreSQL |

Названия этапов в интерфейсе: «Согласование реквизитов и основания ХК» и
«Согласование состава и норм ХК». Термин «шапка» не используется.

Тип ссылки на согласующий — `string?`, по ключу Identity (`Users.Id` — text) и по
соглашению проекта: `WorkTask.AssignedToUserId`, `ProductComposition.ApprovedByUserId`.
Аномалия `HKCard.AuthorId` типа `uuid` в этом не воспроизводится.

Согласование живёт в отдельном сервисе `HKApprovalService`, а не в `HKCardService`:
у него своя модель данных, свои права и своя транзакция. Смешивание с правкой
карты в одном методе и позволяло обходить блокировки.

#### Соответствие этапов общему статусу

`HKCardStatus` не расширялся. Общий статус — отображение рабочего жизненного
цикла, а не источник блокировок.

| Состояния этапов | Общий статус |
|---|---|
| хотя бы один этап `OnReview` | `OnReview` |
| иначе хотя бы один этап `RevisionRequired` | `RevisionRequired` |
| иначе оба этапа `Draft` или приняты | `Draft` |
| карта в архиве | `Archived` — не вычисляется, сохраняет свой смысл |
| карта удалена | `Deleted` — не вычисляется, сохраняет свой смысл |

Вычисление никогда не возвращает `Archived` или `Deleted` в активное состояние.
Принятые реквизиты при `Draft`-составе дают общий `Draft`: автор готовит
следующий этап. `Approved` в этом PR не устанавливается: окончательное принятие
состава закрыто до появления хранилища принятой структуры.

#### Блокировки по частям

| Часть | Блокируется при | Разрешение |
|---|---|---|
| Реквизиты и основание | этап реквизитов `OnReview` или `Approved` | `HK.Work` |
| Состав и нормы | этап состава `OnReview` | `HK.Work` |
| PDF | вместе с реквизитами | `HK.Attachment.Edit` |

Общий статус для блокировок не годится: при рассмотрении реквизитов статус карты
один и тот же, но реквизиты закрыты, а структура доступна автору.

#### Права

| Действие | Право |
|---|---|
| Создание и редактирование любой части | `HK.Work` |
| Отправка этапа на согласование | `HK.Submit` — новое неуровневое право |
| Принятие этапа | `HK.Approve` |
| Возврат этапа | `HK.Review` |

`HK.Submit` неуровневое: у автономной карты уровень не определён до вывода по
структуре, поэтому уровневые права отправки к ней неприменимы. `HK.Work` само по
себе не даёт ни отправки, ни принятия, ни возврата.

Согласующим назначается конкретный пользователь с действующим полномочием и из
филиала карты. Роль не требуется: согласующим может быть начальник подразделения.
Системный администратор не подменяет назначенного согласующего молча.

Общий переключатель `ChangeStatusAsync` для карт с этапами закрыт: переход
`OnReview`, `RevisionRequired` и `Approved` принадлежит конкретному этапу.
Архивирование и удаление сохранены — они не являются этапом.

#### Задачи

| Событие | Задача |
|---|---|
| Отправка этапа | `HKDetailsReview` или `HKCompositionReview`, адресная, на назначенного согласующего |
| Принятие или возврат | задача рассмотрения закрывается |
| Возврат | `HKRevision` первоначальному автору |
| Повторная отправка | открытые задачи рассмотрения не дублируются |

Задачи пересчёта ИК не создаются. Изменение карты, состояний этапов, задач и
аудита выполняется в одной транзакции.

#### 7.1.1. Сущность позиции дерева

`HKCardNode` — позиция собственного дерева. Это **не** замена доменной сущности
`Node` и не элемент справочника техники. Нулевые уровни не вводились:
используется существующий `HKObjectLevel`, `Aggregate` в проекте уже существует.

| Поле | Тип | Назначение |
|---|---|---|
| `Id` | `Guid` | первичный ключ |
| `HKCardId` | `Guid` | принадлежность конкретной карте |
| `ParentId` | `Guid?` | родитель внутри той же карты; `null` — верхняя позиция под корнем `HKCard` |
| `Level` | `HKObjectLevel` | уровень позиции |
| `Name` | `string(200)` | название позиции |
| `Quantity` | `int` | количество, по умолчанию 1 |
| `SortOrder` | `int` | порядок среди siblings, по умолчанию 0 |

`ParentId = null` означает верхнюю позицию под корнем карты, а не создание
дополнительного корня-копии. Уникальность по `Name` не вводится: одинаковые
названия в разных картах и внутри карты не объединяются. Мягкое удаление для
нового дерева не вводится — механизм удаления рабочих позиций вне объёма PR.

#### 7.1.2. Принадлежность карте и родительские связи

Принадлежность одной карте защищена на уровне PostgreSQL, а не только сервисом:

- составной внешний ключ `(HKCardId, ParentId) → (HKCardId, Id)` — простой FK
  по `ParentId` не гарантировал бы, что родитель принадлежит той же карте;
- для этого на `HKCardNodes` задан уникальный ключ `(HKCardId, Id)`;
- то же для конечных строк: `HKCardItem` связан с позицией составным ключом
  `(HKCardId, HKCardNodeId) → (HKCardId, Id)`. Простой FK по `HKCardNodeId`
  разрешил бы привязать строку карты к позиции другой карты;
- самоссылка запрещена CHECK-ограничением `CK_HKCardNodes_NoSelfReference`.

Многошаговые циклы CHECK-ограничением не ловятся — их проверяет сервис
(`SaveTreeAsync`, `HKCardValidationService.ValidateStructureAsync`). Полный
запрет циклов одним CHECK не заявляется.

#### 7.1.3. Конечные строки и материалы

`HKCardItem` сохраняется и используется как конечная строка сборочной единицы
со всеми существующими нормативными полями (`Quantity`, `Volume`, `UnitOfMeasure`,
`Periodicity`, `Notes`, `SortOrder`). Добавлена nullable-связь `HKCardItem.HKCardNodeId`:

- заполнена — строка расположена под структурной позицией;
- `null` — строка непосредственно под корнем карты либо старая строка,
  не включённая в новое дерево.

Существующие строки не перепривязываются автоматически. `HKCardItemMaterial`
сохраняет существующую связь `HKCardItemId`; материал не привязывается напрямую
к `HKCardNode`. Нормативные поля не переносятся из `HKCardItem` в
`HKCardItemMaterial`. Ссылка на справочную `AssemblyUnit` не означает общий
состав: количество, нормы, материалы и расположение принадлежат конкретной
строке конкретной карты.

#### 7.1.4. Количество и порядок

`Quantity > 0` и `SortOrder >= 0` обеспечены CHECK-ограничениями PostgreSQL
(`CK_HKCardNodes_QuantityPositive`, `CK_HKCardNodes_SortOrderNonNegative`)
и продублированы в сервисной проверке. Название непустое — третий CHECK
`CK_HKCardNodes_NameNotBlank`.

#### 7.1.5. Проверки уровней и пропусков

Полная логика вывода уровня карты и редактор дерева остаются следующим PR.
В этом PR **не вводятся** запреты, исключающие согласованные пропуски уровней.
Неопределённый уровень представлен явно: `HKObjectLevel.Undefined = 0`, а не
значением `Complex`/`Node` и не нулём как заглушкой. Пустое дерево не позволяет
вывести уровень, и это выражено состоянием, а не фиктивным уровнем.

#### 7.1.6. Пустое дерево и согласование

Пустое дерево **не блокирует** согласование реквизитов: `ValidateDraftAsync`
не проверяет структуру. Заполненность структуры проверяется отдельно —
`HKCardValidationService.ValidateStructureAsync`, вызываемый при отправке состава
и норм. Существующий `ChangeStatusAsync` в этом PR **не переключён** на
нереализованный двухэтапный процесс; в нём только добавлена ветка проверки
структуры для автономной карты.

#### 7.1.7. Режим автономной карты

Сценарий различается явно, а не по наличию строк дерева: у автономного черновика
дерево может быть пустым. Добавлено `HKCard.IsAutonomous` (bool, default `false`).
Существующие карты остаются в прежнем режиме и не переключаются автоматически.

Для автономной карты:
- все четыре справочные ссылки объекта могут отсутствовать;
- правило «одна активная ХК на справочный объект» не применяется
  (`EnsureNoActiveDuplicateAsync` возвращается рано);
- отсутствие дерева допустимо для сохранения черновика.

`ValidateExactlyOneObject` и `ObjectExistsAsync` применяются только к неавтономным
картам; для автономных проверки объекта пропускаются.

#### 7.1.8. Ограничения БД и сервисные проверки

CHECK-ограничение `CK_HKCards_ExactlyOneObject` ослаблено условием
`"IsAutonomous" OR (...)`: для автономной карты количество объектных ссылок может
быть нулём. Старые карты защищены прежним условием без изменений; в `Down`
ограничение возвращается в исходном виде.

Частичные уникальные индексы `UX_HKCards_OneActivePer*` **не удалялись и не
изменялись**: их фильтры требуют `ObjectLevel = N`, поэтому автономная карта
с пустыми объектными ссылками под них не попадает. Это подтверждено тестом
`AutonomousCard_NotLimitedByActivePerObject` — две автономные карты создаются
без ограничения.

#### 7.1.9. Границы старого и нового сценария

- Старый сценарий (включение готовых ХК) сохраняется в коде и БД.
- `HKCardComponent`, его API и связанные методы не удаляются.
- ИК не разрабатываются, не адаптируются и не удаляются.
- Марки ГСМ остаются ссылками на общий справочник.
- Пользователи, Identity, роли, полномочия и отделы не затронуты.
- Сброс тестовых данных не выполняется.

#### 7.1.10. Миграция и тесты

Миграция `AddAutonomousTree`: колонка `IsAutonomous`, колонка `HKCardNodeId`,
таблица `HKCardNodes`, ослабление `CK_HKCards_ExactlyOneObject`, четыре CHECK
на позициях, составные внешние ключи. Предметные данные не удаляются и не
переносятся. Проверена на отдельной базе `chernika_pr2_mig`, рабочая база не
затрагивалась.

Тесты `HKCardNodeTreeIntegrationTests` на PostgreSQL (не InMemory): сохранение
дерева; несколько независимых карт; родитель из другой карты; строка из другой
карты; самоссылка; многошаговый цикл; количество и порядок; нормы и материалы
через `HKCardItem`; пустой автономный черновик; старые карты сохраняют
обязательную объектную привязку; автономная карта не ограничена проверкой
одной активной карты на объект.

#### 7.1.11. Зависимость от источника номера

В исходной реализации PR № 2 `CreateAsync` подставлял автономной карте временный
номер вида `AUTONOMOUS-{Id}`. Это было временное решение: при отсутствии
утверждённого источника кода нужно было чем-то заполнить `Code`.

PR № 2.1 этот номер **удалил**. Временный production-номер не вводится: публичное
создание автономной карты завершается понятной контролируемой ошибкой, и проверка
стоит первым действием метода — до изменения состояния `DbContext`, до
аудита и до записи, поэтому отказ не оставляет подготовленных записей.

Тестовые автономные карты создаются тестовой фикстурой с явно заданным тестовым
номером; новым правилом нумерации это не является.

**Снято в PR № 3.** Источник номера определён (§ 3.6): средняя часть —
введённое `HKCard.Name`. Запрет автономного `CreateAsync` удалён, форма создания
появилась, номер формируется сервером как `ХК-{название}-{год}`.

#### 7.1.12. Единое право HK.Work (выполнено в PR № 2.2)

Уровневые `Create`/`EditDraft` не выражают доступ к карте: её уровень может быть
не определён и выводится из верхних строк дерева.

Принято и реализовано единое право **`HK.Work`** — создание и редактирование ХК
независимо от `ObjectLevel` и `IsAutonomous`. Fallback «HK.Work или уровневое
право» **не применяется**: иначе оставшиеся уровневые разрешения продолжали бы
действовать, а индивидуальный запрет `HK.Work` не запрещал бы операцию.

##### Конкурентное сохранение дерева

`SaveTreeAsync` получает необязательный `expectedRowVersion` и **обновляет запись
карты** в той же транзакции, что дерево и аудит. Карта загружается отслеживаемой,
поэтому EF отправляет UPDATE с условием по `xmin`: параллельная правка карты
приводит к отказу, а не к молчаливой перезаписи дерева.

Точное изменение публичного метода:

```
- public Task SaveTreeAsync(Guid cardId, IReadOnlyList<HKCardNodeWrite> positions, CancellationToken ct = default)
+ public Task SaveTreeAsync(Guid cardId, IReadOnlyList<HKCardNodeWrite> positions,
+                           uint? expectedRowVersion = null, CancellationToken ct = default)
```

Связанные вызовы: новые аргументы позиционно-необязательные и добавлены перед
`ct`, поэтому существующие вызовы `SaveTreeAsync(cardId, positions)` и
`SaveTreeAsync(cardId, positions, ct)` сохраняют смысл только при передаче
`ct` именованно. В коде вызовы передают токен отмены именованно
(`ct: ct`) либо используют перегрузку без него.

Это защита от **потери обновления карты**, а не сериализация операций над
деревом: два параллельных вызова `SaveTreeAsync` по одной карте по-прежнему не
выстраиваются в очередь, последний записанный набор побеждает. Полная
сериализация потребовала бы отдельного решения владельца.

Необязательный параметр **не является** полной защитой от отправки устаревшего
набора из интерфейса: если вызывающий код версию не передал, проверка не
действует. Будущий редактор дерева обязан передавать версию, прочитанную при
загрузке.

Остаточные исправления, выполненные в PR № 3:

- метка `UpdatedAt` карты увеличивается хотя бы на тик, если источник времени её
  не изменил (фиксированный `TimeProvider`, остановленные часы). Без этого EF не
  формировал UPDATE вовсе, токен `xmin` не попадал в `WHERE`, и конкурентная
  правка проходила незамеченной;
- тест переноса сохраняемой позиции из удаляемой ветви исправлен: сохраняемый
  узел изначально находился рядом с удаляемой ветвью, а не внутри неё, и
  сценарий порядка удаления не проверялся;
- описание `expectedRowVersion` уточнено, заявлен фактический результат полного
  прогона PR № 2.2.

#### 7.1.13. Создание автономной ХК (выполнено в PR № 3)

##### Схема Name и Code

| Свойство | Тип | Предел | Назначение |
|---|---|---|---|
| `HKCard.Name` | `string?` | 200 | Название объекта, вводится автором. У старых карт отсутствует — это допустимо |
| `HKCard.Code` | `string` | 260 | Номер. Прежний предел 50 не вмещал название |

Предел номера покрывает худший случай: префикс `ХК-` (3) + название (200) +
разделитель (1) + год (4) + суффикс `-N`. Название ради лимита колонки **не
обрезается молча**: превышение отклоняется проверкой с текстом пользователю.
Название не уникально, карты по совпадению не объединяются.

##### Правила генерации номера

Два раздельных сценария:

| Сценарий | Источник средней части | Правило |
|---|---|---|
| Старый | `ResolveObjectCodeAsync` — справочный код | Прежний алгоритм без изменений |
| Автономный | `HKCard.Name` | `ХК-{название}-{год}` |

Год берётся из `TimeProvider`, отдельной трактовки даты не вводится. Суффикс
совпадения выделяется по длине остатка строки, а **не** наивным делением по
`-`: название само содержит дефисы. Проверка номера автономной карты —
отдельное выражение `AutonomousCodeRegex`; прежний `CodeRegex`, рассчитанный на
справочный код, к автономному номеру не применяется.

Номер формируется при создании и далее неизменен: правка названия документ не
перенумеровывает. Номер не принимается из запроса.

##### Что не доверяется клиенту

Сформированный номер, версия, автор, служебные даты, а также уровень карты и
режим существующей карты. `ApplyUpdate` уровень и справочные ссылки не
применяет вовсе; переключение между старым и автономным сценариями отклоняется
явно. Изменяемым остаётся `NodeId` — единственная допустимая смена привязки,
влекущая переформирование номера.

##### Конкурентное создание

Уникальный индекс `IX_HKCards_Code_Version` отвергает повтор номера и версии.
Проверки «номер пока свободен» перед вставкой недостаточно: два создания могут
выбрать один номер, и доказательством служит индекс. Конфликт обрабатывается
контролируемо: транзакция откатывается целиком, аудит не пишется, пользователь
получает сообщение о конфликте, а не 500.

Карта и аудит записываются в одной транзакции и в таком порядке: сначала карта,
потом аудит. При прежнем порядке запись аудита осталась бы без документа —
`AuditService.CreateLogAsync` **только добавляет запись в трекер** и само
`SaveChangesAsync` не вызывает, поэтому сохранение делает вызывающий. После
перестановки порядка это означало бы, что запись аудита не сохраняется вовсе:
сначала `SaveChanges` (карта), затем `CreateLogAsync` без сохранения. Поэтому
после аудита нужен явный второй `SaveChangesAsync` — внутри той же транзакции.

Ошибка была поймана существующим тестом `HkCardMaterialSetSyncIntegrationTests`:
он проверяет наличие записи аудита `Created`. В полном прогоне после переноса
аудита записи `Created` не осталось ни одной. Добавлена также проверка в
`HKAutonomousCardIntegrationTests`, что аудит создания пишется, и что отказ в
создании не оставляет записи аудита.

##### Границы этапа

Готово: открыть форму, заполнить реквизиты и название, сохранить автономную ХК
в `Draft`, получить сформированный номер, открыть и отредактировать реквизиты.
Пустая структура допустима, `ObjectLevel` остаётся `Undefined`.

Не реализовано: два этапа согласования, вывод уровня из дерева, редактор дерева,
публикация состава, хранение последней принятой структуры, ИК, включение
готовых ХК.

Одноэтапный `ChangeStatusAsync` **не является** готовым жизненным циклом
автономной карты. Пока двухэтапный процесс не реализован, окончательное
утверждение автономной карты через старый процесс запрещено: `ChangeStatusAsync`
отклоняет переход в `Approved` с объяснением. Сохранение и редактирование черновика
работают.

#### 7.1.14. Раздельное согласование и снятие старого сценария (PR № 4)

##### Решение владельца: старый процесс не поддерживается

ХК прежнего процесса признаны тестовыми данными. Сохранять, переносить и
адаптировать их не требуется. Отменены требования сохранять старый workflow,
его API и неизменность прежнего поведения.

Целевое состояние: все карты работают по автономному сценарию с двумя этапами.

Сделано в этом PR:

- общий переключатель `ChangeStatusAsync` закрыт для карт с этапами: переходы
  `OnReview`, `RevisionRequired` и `Approved` принадлежат конкретному этапу;
- API создания больше не принимает создание карты старого сценария: значение
  `IsAutonomous` из запроса игнорируется, карта всегда создаётся автономной,
  уровень и справочные ссылки из запроса не применяются;
- новое право `HK.Submit` неуровневое; уровневые права отправки старого сценария
  не переносятся и не заменяются автоматически.

Не сделано и вынесено за границы PR:

- ветвь `CreateAsync` для `IsAutonomous = false` сохранена как представление
  ранее созданных строк. Публичного вызова, создающего такую карту, не осталось
  (API закрыт), но сервисный путь ещё существует и будет удалён вместе с
  очисткой данных;
- обработчики прежнего процесса в `HKEdit.razor` оставлены для чтения старых

#### 7.1.16. Завершение раздела 1 (продолжение)

##### Гонка решений: TOCTOU-разрыв версии

Обнаружено при написании регрессионного теста: две параллельные отправки
реквизитов с одной исходной версией **обе завершались успешно**.

Причина. Версия сверялась со снимком `PersistedCardState`, прочитанным **до**
открытия транзакции. Запись же шла по строке, перечитанной **внутри** транзакции.
Если победившая команда фиксировалась между этими двумя чтениями, проигравшая
перечитывала уже обновлённую строку, её токен совпадал с её собственной
фиксацией, и `UPDATE` проходил. Оптимистичный токен не срабатывал, потому что
проверялся не тот снимок.

Исправление: версия сверяется повторно по строке, прочитанной внутри транзакции
команды, во всех пяти командах этапов. Предварительная проверка по снимку вне
транзакции сохранена — она отвечает за устаревший экран.

##### Эталон реквизитов

`UpdateAsync` сравнивал реквизиты с отслеживаемым экземпляром. При штатном вызове
из формы входной объект — тот же отслеживаемый экземпляр, поэтому подмена полей
была невидима: команда считала, что реквизиты не менялись, и пропускала их вместе
с запрещёнными строками. Сравнение переведено на отдельную проекцию
`AsNoTracking` (`StoredDetails`).

##### Инициализация этапов

Вставка выполняется одним `INSERT ... ON CONFLICT ("HKCardId","Stage") DO NOTHING`.
Ловить произвольный `unique violation` больше не требуется, `ChangeTracker.Clear()`
не используется как замена откату, после вставки состояние перечитывается.

##### Возможности редактирования

Ветка «этапов нет» возвращала полную редактируемость **до** проверки статуса:
архивная и удалённая карта показывались редактируемыми. Отсутствие этапов теперь
разбирается наравне с их наличием.

##### Форма

- Флаги частей при загрузке существующей карты не вычислялись вовсе и оставались
  в состоянии по умолчанию, а общий `canEdit` перезаписывался старой проверкой
  статуса. Общий флаг выводится из флагов частей.
- Реквизиты — `canEditDetails`; строки, нормы, материалы, дочерние ХК —
  `canEditComposition`; PDF — `canEditPdf`; кнопки сохранения — общий `canEdit`.
- У автономной карты `selectedLevel` равен `Undefined`, из-за чего собственные
  строки были скрыты, а блок дочерних ХК показывался. Исправлено: собственные
  строки доступны, блок дочерних ХК скрыт, показан честный информационный
  текст о нереализованном редакторе дерева. Уровень `Node` не подставляется.

`HKCardItem` | `Id` → `SourceItemId`; `Quantity`, `Volume`, `UnitOfMeasure`, `Periodicity`, `Notes`, `SortOrder` | — |
`HKCardItemMaterial` | `GsmMaterialId` → `SourceGsmMaterialId`; `Category` ИЗ СТРОКИ | автор относил марку к категории при заполнении |
`GsmMaterial` | `Name`, `Nd` | читаются из снимка, не через живую ссылку |

Прежних `Type`/`Gost` в модели справочника нет: восстанавливать нечего, и
подставлять справочные аналоги вместо актуальных НД нельзя.

##### Ограничения на уровне PostgreSQL

| Ограничение | Назначение |
|---|---|
`UX_HKCardRevisions_Card_Number` (`HKCardId`,`RevisionNumber`) | номер редакции уникален внутри карты |
`UX_HKCardRevisions_Card_Id` (`HKCardId`,`Id`) | позиция для составного FK указателя |
`UX_HKCardRevisionNodes_Revision_Id` (`RevisionId`,`Id`) | позиция для составного FK родителя |
`UX_HKCardRevisionItems_Revision_Id` (`RevisionId`,`Id`) | позиция для составного FK строки |
FK узлов `("RevisionId","ParentId")` → узлы `("RevisionId","Id")` | родитель принадлежит той же редакции |
FK строк `("RevisionId","NodeId")` → узлы `("RevisionId","Id")` | позиция строки принадлежит той же редакции |
FK материалов `RevisionItemId` → строки `Id` | материал принадлежит своей строке |

`DeleteBehavior.Restrict` для всех связей снимка: физическое удаление карты с её
историей означало бы уничтожение принятых структур.

##### Граница неизменяемости

Зафиксированная редакция не изменяется на месте; следующая фиксация создаёт
новую. Защита от изменения и удаления через прикладной EF-контекст делается
явной и покрывается тестами.

Граница защиты: проверка в сервисе и в `SaveChanges` **не является** защитой от
произвольного SQL администратора, который может выполнить `UPDATE` напрямую.
Разрушительная очистка истории не вводится.

##### PDF

Одного сохранённого `Id` вложения недостаточно: замена PDF удаляет исходный
файл, и ссылка перестала бы что-то означать. Снимок хранит содержимое ссылки —
ключ хранения, имя, размер, содержимое-тип, дату загрузки и `Sha256`.

Фактический механизм:
- `SaveAsync` открывает файл через `FileMode.CreateNew`: запись по занятому ключу
  отвергается, зафиксированный файл не перезаписывается. Новое рабочее вложение
  всегда получает новый ключ `hk/{cardId}/{Guid}.pdf`;
- `DeleteAsync` ПЕРЕД физическим удалением проверяет по `AttachmentStorageKey`, есть ли
  ссылка хотя бы на одну зафиксированную редакцию. Если есть — файл сохраняется;
- проверка выполняется в контексте вызывающего сценария, а не в отдельном
  подключении: отдельное подключение не увидело бы редакцию незакрытой транзакции
  и могло бы обратиться к другой базе, чем обслуживаемая карта;
- при невозможности доказать безопасность удаления файл сохраняется: лишний файл
  лучше потерянного основания. Массовой очистки нет.

Ограничение: `File.Delete` необратим и не откатывается транзакцией PostgreSQL.
Поэтому порядок такой — сначала решение о сохранности принимается по данным, и
только затем файл удаляется. Если в момент проверки появилась новая ссылка от
конкурентной фиксации, файл сохранится лишний раз — это допустимо и безопасно.

Межпроцессной гарантии механизм не даёт: это решение по данным, а не блокировка
файловой системы.

`StorageKey` и путь файловой системы не выдаются наружу: чтение идёт через DTO.
Выдача PDF проверяет доступ к соответствующей карте. Массовое копирование и
очистка вложений не выполняются, новое внешнее хранилище не вводится.

##### Что НЕ объявляется готовым

Окончательное принятие состава, публикация состава, пользовательский сценарий
доработки принятой карты и редактор дерева подключаются следующими PR.


##### Фиксация

`HKCardRevisionService.CaptureAsync(cardId, expectedCardRowVersion)`.

- Источник данных — СОХРАНЁННОЕ состояние: карта, позиции, строки и материалы
  читаются из базы, а не берутся из графа формы, который мог быть не сохранён.
- Получает ожидаемую версию карты и сверяет её с сохранённой; при расхождении
  фиксации нет.
- Согласованность набора обеспечивается транзакцией с уровнем изоляции
  **REPEATABLE READ**. Обычная последовательность SELECT при READ COMMITTED не
  образует согласованный снимок: конкурентная запись рабочей структуры попала бы
  внутрь редакции.
- Владение транзакцией однозначно: если вызывающий уже открыл транзакцию, своя
  не открывается.
- Ошибка не оставляет частичной редакции: запись откатывается целиком.

**Контракт внешней транзакции.** Сервис сам открывает транзакцию только с уровнем
REPEATABLE READ. Внешняя транзакция принимается, если её уровень — REPEATABLE READ
или SERIALIZABLE: оба дают согласованный снимок. Любой другой уровень отклоняется
ДО записи, без попытки открыть несовместимую вложенную транзакцию. Чужую
транзакцию сервис не коммитит и не откатывает: владение принадлежит вызывающему.
`ChangeTracker.Clear()` откатом базы не считается.

**Обязанность вызывающего.** После ошибки фиксации вызывающий workflow НЕ ДОЛЖЕН
продолжать принятие и коммитить операцию как успешную: сервис откатывает только
собственную транзакцию, а чужую оставляет открытой намеренно. Продолжение после
ошибки фиксации — нарушение контракта.
- Конкурентная фиксация: номер редакции уникален внутри карты, версия карты
  общая, поэтому состояться может ровно одна фиксация.

**Фактическая гарантия.** `CaptureAsync` не меняет `RowVersion` карты, поэтому
уникальность `RevisionNumber` НЕ доказывает, что одну рабочую версию можно
зафиксировать один раз. Гарантируется: уникальные номера, согласованное
содержимое каждой редакции, отсутствие частичных записей, контролируемый исход
конфликта. Запрет повторной последовательной фиксации одной версии здесь не
вводится: несколько редакций карты предусмотрены моделью.

Единственность окончательного решения в PR № 6 будет обеспечиваться состоянием
этапа, ожидаемой версией и общей транзакцией, а не `Max(RevisionNumber) + 1`.

**Чего фиксация не делает:** не выставляет `Composition.Approved`, не выставляет
статус карты, не закрывает задачу рассмотрения, не шлёт уведомление «ХК принята»
и не переключает `CurrentAcceptedRevisionId`. Снимок появился бы в обход
согласования, а это ровно то, чего быть не должно.

##### Чтение

`GetAcceptedAsync(cardId)` читает последнюю принятую структуру по указателю.
`GetRevisionAsync(cardId, revisionId)` читает конкретную редакцию с проверкой
принадлежности той же карте.

- Отсутствие `CurrentAcceptedRevisionId` возвращается **явно** как отсутствие
  принятой структуры. Подстановка рабочего дерева была бы незаметной подменой
  черновика принятой картой.
- Источник истины — указатель. Выбор по максимальной дате, максимальному номеру
  или последней созданной записи дал бы иную карту при любом расхождении истории.
- GET ничего не создаёт и не переключает.
- Наружу отдаются отдельные DTO с неизменяемыми коллекциями; EF-сущности с
  изменяемыми коллекциями не выдаются. `StorageKey` и путь файловой системы в
  DTO не входят.
- API-чтение принятой структуры в этом PR не открывалось: это отдельная
  поверхность, которой нужен собственный контракт.

##### Защита от изменения

`HKCardRevisionImmutabilityInterceptor` — `SaveChangesInterceptor`, запрещающий
состояния `Modified` и `Deleted` для всех четырёх снимковых сущностей. `Unchanged`
разрешён: снимок может находиться в контексте только потому, что его загрузили.

**Граница защиты указана явно.** Перехватчик перехватывает лишь `SaveChanges` и
`SaveChangesAsync`. Он НЕ перехватывает `ExecuteUpdate`, `ExecuteDelete` и
произвольный SQL. Проверено: в прикладном коде путей изменения снимков через
`ExecuteUpdate`/`ExecuteDelete` нет. Защита — прикладная; произвольный SQL
администратора её не останавливает.

Дополнительно: связи «редакция → строка → материал» объявлены обязательными, поэтому
EF не позволяет удалить родителя с дочерними записями раньше перехватчика. Это более
сильная гарантия и проверяется отдельно через `ExecuteDelete` с ожиданием отказа
ограничения `RESTRICT`.


#### 7.3. Окончательное принятие состава (PR № 6)

##### Единственная команда

`HKApprovalService.ApproveCompositionAsync`. Параллельного endpoint публикации
нет, `CaptureAsync` наружу не открыт, клиент не присылает снимок и не назначает
указатель. Источник принимаемых данных — сохранённая рабочая карта.

##### Условия принятия (все на сервере, по сохранённому состоянию)

аутентифицированный и активный пользователь; эффективное `HK.Approve`; доступ к
филиалу; пользователь — назначенный согласующий; реквизиты `Approved`; состав
`OnReview`; согласующий состава совпадает с согласующим реквизитов; карта не
`Archived` и не `Deleted`; ожидаемая версия актуальна; данные проходят
`ValidateDraftAsync`.

`HK.Work` и `HK.Submit` не заменяют `HK.Approve`. Обхода назначения для
SystemAdmin нет. Фиктивный `Node` ради прохождения валидации не присваивается.

##### Владелец транзакции

`ApproveCompositionAsync` открывает общую транзакцию с уровнем **REPEATABLE
READ** — тем же, который `HKCardRevisionService` принимает как совместимый.
Вложенная транзакция не открывается, общую транзакцию фиксация не коммитит.

Порядок: повторное чтение и проверка версий и состояний → валидация → фиксация
структуры → проверка принадлежности редакции → `CurrentAcceptedRevisionId` →
`Composition.State = Approved` → `ApprovedAtUtc` → `HKCard.Status = Approved` →
`ReviewerId` и `ApprovedDate` → закрытие задач этого этапа → журнал, аудит,
уведомление → Commit.

Любая ошибка откатывает операцию целиком. `ChangeTracker.Clear` откатом не
считается.

##### Данные решения

| Поле | Смысл |
|---|---|
`HKCardRevision.AcceptedAtUtc` | момент принятия назначенным согласующим |
`HKCardRevision.AcceptedByUserId` | кто принял (string Identity) |

Заполняются **при создании** редакции. Редакция неизменяема с момента фиксации,
поэтому дописывать их после фиксации нельзя — перехватчик неизменяемости
отклонит изменение. `CapturedAtUtc` (технический момент снятия снимка) датой
утверждения не подменяется.

`HKCard.Id`, `Name`, `Code` и отображаемая `Version` не меняются. Новая `HKCard`
не создаётся. Принятие состава не трогает дату принятия реквизитов,
`EffectiveDate` и `ExpirationDate`.

##### Конкурентность

Ожидаемая версия — версия загрузки экрана; проверяется повторно по строке внутри
транзакции. `Max(RevisionNumber) + 1` защитой от двух окончательных решений не
считается: при одновременном принятии второй получает конфликт версии либо
нарушение уникальности номера, и операция откатывается целиком.

Повторный запрос после успеха отказ даёт без побочных эффектов: следующая
редакция не создаётся, уведомление не дублируется. Автоматического повтора на
более свежих данных нет.

##### Защита принятой карты от правки

Общий запрет `EnsureNotAccepted` действует в `EnsureEditDraftAccessAsync`
(`SaveTreeAsync`), в замене и удалении PDF, в `HKCardItemService`. Состав
заблокирован и по состоянию этапа `Approved` — прежняя проверка смотрела только
на `OnReview`.

`ChangeStatusAsync` не может перевести карту в `Approved` **вовсе**, независимо от
наличия этапов: раньше запрет действовал только для карт с этапами.

Сценарий начала доработки принятой карты в этом PR не реализован. До него карта
доступна только для чтения.

#### 7.3.2. Завершение целостности записи и окончательного принятия (PR № 6.2)

##### Окончательный контракт `ReplaceMaterialsAsync`

Метод перестал быть проверкой «до записи». Теперь это **защищённая единица
работы**: проверка доступа, состояния, версии и фактическая запись материалов
выполняются в одной транзакции, и `SaveChanges` выполняет сам метод.

Граница сохранения явна: произвольный последующий `SaveChanges` вызывающего больше
не может дописать материалы без проверок. Производных вызовов в проекте не
обнаружено — метод вызывается только из тестов.

Проверки сохранены в полном объёме: `HK.Work`, активность пользователя,
филиальная граница, запреты `Composition.OnReview`/`Approved`, `Approved`,
`Archived`, `Deleted`, запрет правки при наличии принятой структуры. Во время
рассмотрения реквизитов разрешённое заполнение работает.

##### Защита фактической записи от гонки

| Слой | Что делает | Чего не делает |
|---|---|---|
Повторный `SELECT` внутри транзакции | отсекает блокировку, наступившую до открытия транзакции | не защищает запись саму по себе |
Конфликтующий `UPDATE "HKCards" ... WHERE "Id" = @id AND "xmin"::text::bigint = @rowVersion` | если версия успела измениться, `UPDATE` не затрагивает ни одной строки и команда отклоняется предметным конфликтом | — |
Та же транзакция | удаление прежнего набора и вставка нового неделимы; частично удалённый набор невозможен | — |
Блокировка строки карты | удерживается до фиксации, поэтому согласование не может вклиниться между проверкой и записью | — |

Наличие транзакции без конфликтующего условия доказательством не считается:
закрывает гонку именно условие `UPDATE`.

Колонка версии карты объявлена как `xmin` типа `xid`, а параметр `uint` выводится
Npgsql как `bigint` — прямое сравнение даёт «оператор не существует: xid =
bigint», поэтому приведение выполняется явно.

##### Изоляция принятия от несохранённых объектов

`RestoreGuardedFields` возвращал лишь часть полей карты и не мешал промежуточному
`SaveChanges` записать несохранённые `Name`, `Purpose`, строки или постороннюю
сущность вызывающего.

Выбран отказ до записи: `EnsureNoPendingCallerChanges` обнаруживает несохранённые
изменения и отклоняет команду с предложением сохранить или отменить их.
`ChangeTracker.Clear` не применяется — он уничтожил бы ввод молча.

Проверен и разрешённый случай: контекст с загруженными, но НЕ изменёнными
сущностями (обычная работа страницы) команду не отклоняет.

##### Стратегия восстановления неуспешной единицы работы

Откат PostgreSQL отменяет записи, но не восстанавливает объекты `ChangeTracker`:
следующий `SaveChanges` того же scope дописывал отменённую редакцию. Явная
стратегия — `RecoverAfterFailureAsync`, выполняемая после завершения транзакции:

- дети отделяются раньше родителя (иначе отделение заголовка снимка при ещё
  отслеживаемых строках обрывает связь и EF бросает исключение вместо
  отсоединения);
- перечисление берётся из `DbSet.Local`, а не из снимка `Entries()`: после
  прерванного `SaveChanges` снимок неполон;
- изменённые и удалённые записи вызывателя перечитываются.

Перехватчик неизменяемости снимков не ослаблен.

##### Принятое содержание на странице

Страница карты показывает номер и дату принятой редакции. Принятых строк, ГСМ и
сборочных единиц она не выводит, поэтому подмены принятого содержания живыми
справочниками нет. Узкий read-only вывод принятого содержимого не добавлялся.


#### 7.3.3. Определение уровня ХК по собственной структуре (PR № 7)

##### Механизм

Одно переиспользуемое место: `Chernika.Domain.Leveling.HKCardLevelRule`.
Чистая функция, без EF Core, HTTP и Blazor. Принимает неизменяемое описание
структуры (`HKTreeShape`) и специальный выбор (`HKObjectLevel?`), возвращает
`HKCardLevelRuleResult` с различиями:

| Статус | Смысл |
|---|---|
`Determined` | уровень однозначно определён |
`Empty` | нет ни позиций, ни конечных строк под корнем |
`NodeRootChoiceRequired` | старшая верхняя позиция — узел, нужен выбор |
`StructureInvalid` | структура недопустима |

Отсутствие выбора и недопустимое значение enum — разные исходы: отсутствие
выбора не считается ошибкой. Нормальное состояние пустого черновика
исключением не является.

Сервисы читают сохранённые данные, строят итоговую структуру команды, вызывают
правило, проверяют доступ и состояние, сохраняют результат транзакционно.
Таблица определения уровня не дублируется в сервисе, контроллере и Razor.

##### Таблица определения уровня

Уровень карты определяется САМЫМ СТАРШИМ уровнем верхних позиций
(`HKCardNode.ParentId = null`). Старшинство: Complex → EquipmentModel →
Aggregate → Node. Числовые значения enum обратны и для старшинства не
используются.

| Старший верхний уровень | Уровень карты |
|---|---|
`Complex` (верхнее изделие) | `Complex` — ХК комплекса |
`EquipmentModel` | `EquipmentModel` — ХК изделия |
`Aggregate` (верхний агрегат) | `EquipmentModel` — ХК изделия |
`Node` + выбор `Aggregate` | `Aggregate` |
`Node` + выбор `EquipmentModel` | `EquipmentModel` |
`Node` без выбора | `Undefined`, требуется выбор |
нет позиций, но есть конечные строки под корнем | `Node` — ХК узла |
нет ни позиций, ни строк | `Undefined` — пустая карта |

Уровень не вычисляется по названию, номеру, первой запрошенной записи,
`SortOrder`, количеству строк и справочным связям. Порядок позиций на
результат не влияет. Одноимённые позиции не объединяются.

##### Таблица допустимых связей и пропусков

| Родитель | Допустимый потомок |
|---|---|
`Complex` (комплекс) | `EquipmentModel`, `Aggregate`, `Node` |
`EquipmentModel` (изделие) | `Aggregate`, `Node` |
`Aggregate` (агрегат) | `Node` |
`Node` (узел) | только конечные строки сборочных единиц |
любой уровень | конечные строки (`HKCardItem`, `HKCardNodeId = null`) |

Пропуски промежуточных уровней разрешены: изделие может содержать узел без
агрегата, агрегат может содержать сборочную единицу без узла. Разрешение
пропускать агрегат и узел не распространяется на произвольное исключение
других уровней — таблица исчерпывающая.

Запрещено: самоссылки, циклы, родитель вне дерева этой карты, движение вверх
по уровням (потомок не младше родителя), `Undefined` и неизвестное значение
enum у позиции.

Кандидат уровня определяется по старшему уровню независимо от допустимости:
наличие старшей позиции не делает допустимыми пропуски и связи остальных.
Допустимость дерева и определение уровня — разные результаты.

`Complex` — допустимый уровень самой ХК. Вложенная копия корня как
структурная позиция `Complex` ради вычисления уровня не создаётся.

##### Поле и команда выбора верхнего узла

Поле: `HKCard.NodeRootCardLevel`, тип `HKObjectLevel?`, nullable.
Допустимые значения: `null`, `Aggregate`, `EquipmentModel`.

Хранится отдельно от вычисляемого `ObjectLevel`. Общий `ObjectLevel` из
запроса не принимается как произвольно устанавливаемое значение.

Правило сброса: когда старший верхний уровень перестаёт быть `Node`, прежний
выбор обнуляется и перестаёт влиять на вычисление. Скрыто устаревший выбор
не хранится.

Команда: `HKCardService.SetNodeRootCardLevelAsync(cardId, choice,
expectedRowVersion)`. Проверяет доступ, `HK.Work`, возможность редактировать
состав, фактический верхний уровень по сохранённой структуре; выбор и
вычисленный уровень сохраняются атомарно в одной транзакции с проверкой
`RowVersion`.

HTTP: `POST /api/HKCards/{id}/node-root-level`, контракт
`SetNodeRootCardLevelRequest(Choice, RowVersion)`. 204 при успехе, 400 при
неприменимом выборе или недопустимом значении, 409 при конфликте версии.

Существующего подходящего поля не нашлось: `NodeId`, `AggregateId`,
`EquipmentModelId`, `ComplexId` — справочные связи объекта, а не выбор.

##### Точки пересчёта рабочего уровня

| Команда | Учитываемый итог |
|---|---|
`SaveTreeAsync` | входной набор позиций + сохраняемые конечные строки + действующий выбор |
`UpdateAsync` | итоговый набор конечных строк после синхронизации |
`SetNodeRootCardLevelAsync` | сохранённая структура + новый выбор |

Правило применяется до `SaveChanges`: недопустимая структура отклоняется, а не
сохраняется наполовину. Правка только названия, назначения, норм или ГСМ
структуру не меняет и уровень не меняет.

Для неавтономных карт уровень не пересчитывается: он приходит из справочного
объекта.

##### Интеграция с согласованием

Первый этап: пустое дерево, `Undefined` и отсутствующий выбор верхнего узла
отправку реквизитов не блокируют.

Второй этап: отправка состава требует допустимой структуры и однозначно
определённого уровня.

Окончательное принятие повторяет проверку внутри своей транзакции по
сохранённым данным и сверяет сохранённый `ObjectLevel` с вычисленным. Уровень
молча не исправляется: несоответствие — понятный отказ с необходимостью
доработки и повторной отправки.

##### Реестр и чтение

Проекции списка и реестра отдают фактический `ObjectLevel`. Условия
«`IsAutonomous` → всегда не определён» в проекциях нет: `ObjectCode` и
`ObjectName` остаются пустыми, потому что у автономной карты нет справочной
привязки, а сам уровень — реальный вычисленный. Правила фильтрации и
пагинации не менялись.

`GET` не пересчитывает и не записывает уровень: `GetLevelProjectionAsync`
только читает. В DTO чтения передаются вычисленный `ObjectLevel`,
`NodeRootCardLevel`, `NeedsNodeRootChoice` и `LevelReason`.

##### Миграция

`20261015125345_AddHKCardNodeRootCardLevel`: nullable-колонка `integer`,
ограничение `CK_HKCards_NodeRootCardLevel` (`NULL` или 2, 3). Массового
вычисления старых значений нет. Применена на `chernika_migtest` после
`verify-db-target.ps1` и подтверждения `current_database()`.

##### Контракт для PR № 8 — редактора структуры

Редактор дерева может опираться на:
- `HKCardLevelRule` как единственный источник правил;
- `SaveTreeAsync` — итоговый набор позиций, уровень считается внутри;
- `UpdateAsync` — итоговый набор конечных строк;
- `SetNodeRootCardLevelAsync` и `GetLevelProjectionAsync` для выбора;
- DTO чтения с `NeedsNodeRootChoice` и `LevelReason`.

Требуется от PR № 8: перенос конечной строки под позицию и обратно под корень
через `UpdateAsync` (пересчёт уже учитывает оба случая), представление
причины неопределённости в интерфейсе.


#### 7.3.4. Исправление определения и сохранения уровня ХК (PR № 7.1)

##### Исправленная таблица определения уровня

Уровень карты на ступень выше уровня своей старшей верхней позиции
(`ParentId = null`). Старшинство позиций: изделие → агрегат → узел.

| Старшая верхняя позиция | Уровень карты |
|---|---|
`EquipmentModel` (верхнее изделие) | `Complex` — ХК комплекса |
`Aggregate` (верхний агрегат) | `EquipmentModel` — ХК изделия |
`Node` + выбор `Aggregate` | `Aggregate` |
`Node` + выбор `EquipmentModel` | `EquipmentModel` |
`Node` без выбора | `Undefined`, требуется выбор |
нет позиций, есть конечные строки под корнем | `Node` — ХК узла |
нет ни позиций, ни строк | `Undefined` |

`Complex` получается единственным способом — от верхнего изделия. Структурная
позиция `Complex` отклоняется понятной доменной ошибкой: это дополнительная
копия корня, которая для вычисления уровня не нужна.

Таблица допустимых связей не расширялась: изделие → агрегат или узел;
агрегат → узел; узел → конечные строки. Новых неподтверждённых пропусков не
добавлено.

##### Правило сохранения и сброса выбора

`NeedsNodeRootChoice` означает «выбор ещё необходим», а не «выбор неприменим».
По нему сбрасывать действующий выбор было нельзя — это и было ошибкой.

| Ситуация | Выбор |
|---|---|
старшая верхняя позиция `Node`, выбор действующий | сохраняется |
повторное сохранение того же дерева | сохраняется |
правка названия позиции, количества, порядка | сохраняется |
сохранение строк | сохраняется |
правка реквизитов | сохраняется |
старшая верхняя позиция перестала быть `Node` | обнуляется, уровень считается по новому набору |
после этого структура снова начинается с узла | требуется новый явный выбор |

##### Источник итоговых строк

| Команда | Позиции | Конечные строки |
|---|---|---|
`SaveTreeAsync` | входной набор команды | сохранённые (команда строки не меняет) |
`UpdateAsync` | сохранённые | ИТОГОВЫЙ набор команды после применения; при заблокированном составе — сохранённые |
`SetNodeRootCardLevelAsync` | сохранённые | сохранённые |

Правило больше не читает строки из базы «поверх» подготовленных изменений: ранее
уровень считался по ПРЕЖДЕНИМ строкам, и строки команды сохранялись уже с
неверным уровнем. Промежуточный `SaveChanges` ради получения нового количества
не делается.

##### Перенос конечных строк

`DesiredItem` теперь несёт `HKCardNodeId`, и синхронизация сохраняет его.
Наличие поля в сущности доказательством сохранения командой не являлось: до
исправления перенос строки под позицию и обратно под корень молча терялся.
При переносе сохраняются идентификатор строки, нормы и материалы.

##### Соответствие уровня при отправке

Перед `SubmitCompositionAsync` проверяются структура, наличие обязательного
выбора, определённость результата и равенство сохранённого `ObjectLevel`
вычисленному. При несоответствии — понятный отказ без задач и смены состояния.
Уровень в команде отправки молча не исправляется. Повторная проверка внутри
транзакции при принятии сохранена. Первый этап по-прежнему не требует
заполненной структуры или определённого уровня.

##### Реестр и DTO

В `HCRegistry.razor` убрано правило «автономная карта всегда не определён»:
отображается фактический `ObjectLevel`, `Undefined` — только при реальном
`Undefined`. Справочные `ObjectCode`/`ObjectName` фиктивно не заполняются.
Проверено вызовом настоящей проекции `GetRegistryPageAsync`, включая фильтр по
уровню без требования справочной привязки.

DTO чтения отдаёт сохранённый уровень, специальный выбор, `NeedsNodeRootChoice`
и `LevelReason`. GET ничего не записывает.

##### Устойчивость правила

`Resolve` возвращает `StructureInvalid` вместо исключения. Проверены
повторяющиеся идентификаторы, `Guid.Empty`, неизвестные уровни, `Undefined`,
самоссылки, циклы и отсутствующий родитель. Старшинство неизвестного уровня
больше не равно старшинству старшего: для него `int.MaxValue`, иначе
значение по умолчанию кортежа делало мусор самым старшим. Дополнительно
введён `SeniorTopLevel` — команды проверяют фактический верхний уровень сами.

##### Контракт для PR № 8 — редактора структуры

Редактор опирается на исправленный контракт:
- `HKCardLevelRule` — единственный источник правил, уровень на ступень выше
  старшей верхней позиции;
- позиция `Complex` в дереве недопустима: редактор не должен предлагать её;
- `SaveTreeAsync` и `UpdateAsync` считают уровень сами по итоговой структуре;
- `SetNodeRootCardLevelAsync` — только при фактическом верхнем узле;
- `GetLevelProjectionAsync` и DTO дают признак необходимости выбора и причину.

Открытые для PR № 8: представление дерева с запретом позиции `Complex`,
перенос строк между позициями и корнем через `UpdateAsync`, показ причины
неопределённости в интерфейсе.


#### 7.3.5. Редактор собственной структуры, разделы и итоги (PR № 8)

##### Проверка основы PR № 7.1

Подтверждено перед началом работы: верхнее изделие даёт ХК Complex, верхний
агрегат — ХК EquipmentModel, верхний узел — Aggregate или EquipmentModel по
явному выбору, только конечные строки под корнем — ХК Node, пустая структура —
Undefined. Позиция `Complex` отклоняется. Выбор `NodeRootCardLevel` сохраняется,
пока старшая верхняя позиция — узел, и сбрасывается, когда перестаёт быть
применимым. Пересчёт уровня идёт по итоговым строкам команды. Предварительный
коммит не потребовался.

##### Схема разделов

Сущность `HKCardSection`:

| Поле | Тип | Примечание |
|---|---|---|
`Id` | Guid | первичный ключ |
`HKCardId` | Guid | карта; FK с каскадным удалением |
`SectionType` | `HKCardSectionType` | Oils / Greases / Fuels, хранится как int |
`SortOrder` | int | верхний порядок раздела |

Уникальный индекс на `(HKCardId, SectionType)`: один раздел каждого типа на
карту. Разделы не создаются автоматически при открытии карты — пустое
информационное состояние не является записью базы.

Раздел не входит в `HKObjectLevel` и не влияет на уровень карты. У него нет
количества экземпляров и собственных норм.

##### Наследование принадлежности

`HKCardNode.SectionId` заполняется ТОЛЬКО у верхней позиции (`ParentId = null`).
`HKCardItem.SectionId` заполняется ТОЛЬКО у строки под корнем
(`HKCardNodeId = null`). Вложенные позиции и строки наследуют раздел своего
корня; независимо редактируемый раздел у каждого вложенного узла не хранится,
поскольку создал бы противоречивую принадлежность одной ветки.

Оба FK — `Restrict`: раздел нельзя удалить вместе с ветками.

##### Правила порядка и нумерации

`HKStructureNumbering` — единственное место, где строится представление.

- Раздел отображается строкой во всю ширину без количества и норм.
- Разделы и самостоятельные ветки без раздела делят ОДНУ верхнюю
  последовательность. Обязательной технической позиции «Без раздела» нет.
- Позиция, принадлежащая разделу, самостоятельной веткой не является и повторно
  не выводится.
- Номер отражает фактический путь: раздел → структурные родители → строка.
  Пропущенный уровень техники пустого сегмента не создаёт.
- Потомки одного родителя — позиции и строки — упорядочиваются ОДНИМ списком.
  При равном `SortOrder` порядок детерминирован: позиции раньше строк, затем по
  идентификатору.
- Количество позиции дополнительных номеров не создаёт.
- Номера вычисляются, не редактируются и не используются вместо `Id`.

##### Формулы «на один» и «всего»

`HKCardItem.Volume` — масса или объём ОДНОЙ сборочной единицы.

- одна конечная строка: `Volume`;
- «на один экземпляр» позиции: `Σ` по вложенным строкам
  `Volume × Quantity строки × Π Quantity позиций строго ПОД позицией`;
- «всего в ХК» для позиции: то же × `Quantity` самой позиции ×
  `Π Quantity` её строгих предков.

Проверяемый пример: агрегат × 2, узел × 3, сборочная единица × 4,
`Volume = 500 г` → одна единица 500 г, один узел 2000 г, один агрегат 6000 г,
вся ветка 12000 г (12 кг).

Собственное количество позиции в её «на один» не входит — иначе оно
умножалось бы дважды. Итог родителя и уже включённые в него итоги детей
одновременно не складываются: итог строится только из конечных строк.

Материалы расходными строками не являются: одна строка учитывается один раз
независимо от количества марок и категорий. Периодичность и коэффициенты ИК не
участвуют.

##### Поддерживаемые единицы

`HKUnitCatalog`: кг (масса, ×1000), г (масса, ×1), л (объём, ×1). Сравнение
регистронезависимое, точки и пробелы отбрасываются.

Масса хранится в базовых граммах, объём — в литрах; величины не смешиваются.
Отображение: `1,5 кг (1500 г)`, `120 л`. `decimal`, без float; промежуточные
суммы не округляются, округление — только на границе показа.

Нераспознанная единица не угадывается и не превращается в ноль: итог помечается
неполным с диагностикой и не может быть прочитан как достоверная полная сумма.
Литры в килограммы не переводятся.

Один механизм `HKStructureTotals` принимает и рабочее дерево, и принятую
редакцию — формулы не дублируются.


##### Контракт атомарного сохранения структуры

`HKCardService.SaveStructureAsync(SaveHKCardStructureCommand)`.

Команда принимает итоговые разделы, позиции, строки с материалами, специальный
выбор верхнего узла и ожидаемую версию, полученную при загрузке карты.
Служебные свойства (номер, статус, автор, указатель принятой редакции)
редактируемыми не являются и в контракт не входят.

Порядок в одной транзакции: доступ и редактируемость состава → версия →
проверка итогового графа → синхронизация разделов, позиций, строк и материалов →
вычисление уровня → аудит → фиксация.

Граф проверяется ДО открытия транзакции и до любых изменений отслеживаемого
состояния: отказ не оставляет подготовленных записей, которые дописал бы
последующий `SaveChanges`.

Проверки: уникальность типа раздела на карту; раздел ветки принадлежит этой же
карте; родитель позиции и узел строки находятся в том же наборе; позиция
`Complex` отклоняется; строка без сборочной единицы не пишется; непустой раздел
не удаляется молча; назначения марок проверяются общими правилами ГСМ.

Уровень считается по ИТОГОВОЙ структуре команды: строки ещё не сохранены,
читать их из базы означало бы считать прежние данные.


##### Расширение принятого снимка разделами

Миграция `20261016121415_AddRevisionSections`.

Новая сущность `HKCardRevisionSection`: `Id`, `RevisionId`, `SectionType`,
`SortOrder`. Собственная таблица, а не ссылка на рабочий `HKCardSection`:
принятая редакция воспроизводится из снимка и не должна зависеть от последующих
правок рабочей карты.

Принадлежность разделом фиксируется у снимковой верхней позиции
(`HKCardRevisionNode.SectionId` при `ParentId = null`) и у снимковой конечной
строки под корнем (`HKCardRevisionItem.SectionId` при `NodeId = null`).
Вложенные позиции и строки наследуют раздел корня и значения не получают.

Составной FK `{RevisionId, SectionId}` → `{RevisionId, Id}` с `Restrict`:
принадлежность ветки не может указывать на раздел другой редакции.

`CaptureAsync` пишет снимки разделов и принадлежность. Раздел ветки, не
попавший в снимок, — отказ фиксации: молча превращать ветку в «без раздела»
нельзя.

##### Чтение принятой структуры и итогов

`HKAcceptedStructureDto` дополнен списком `Sections` (`HKAcceptedSectionDto`:
`SectionId`, `SectionType`, `Name`, `SortOrder`). Принадлежность передаётся у
снимковой позиции и строки.

`GetAcceptedTotalsAsync` считает итоги принятой редакции ТОЛЬКО из снимковых
`Quantity`, `Volume`, `UnitOfMeasure` и принадлежности разделам. Расчётный
механизм тот же `HKStructureTotals`, что и для рабочего дерева: формулы не
дублируются, различаются только входные данные.

Редакция, принятая до появления разделов, читается без разделов: снимковых
разделов у неё нет, и подстановка рабочих не выполняется.

##### PR № 8.1 — восстановление работы с черновиком и завершение редактора

| (этот раздел) | Состояние загрузки, поколения загрузки, дефекты редактора, версионные тесты |

**CircuitDbLock.** Причина ошибки «Вложенный захват» — оба пути сразу:
реальная вложенность (`LoadApprovalStateAsync` брал блокировку внутри уже

вызывался под блокировкой, которая сама брала блокировку) и конкуренция
(`MainLayout.RefreshAccessFlagsAsync` из `OnAfterRender` в одном circuit с
загрузкой карты). Проверка по счётчику глубины эти случаи не различала и
выдавала ложную ошибку вложенности. Теперь конкурентный захват ЖДЁТ
освобождения (предел ожидания 60 с, затем понятная ошибка вместо зависания),
а вложенность исключена явными границами владения: блокировку получает
верхнеуровневая операция, внутренние методы пути её не получают.

**Состояние загрузки.** `HkEditLoadState` (Loading / Ready / Error / NotFound /
Forbidden) вместо одного признака загрузки. Обязательные данные собираются во
временный результат и публикуются целиком; при ошибке не показывается пустая
карточка как загруженный документ, а предлагается «Повторить загрузку».
История версий и названия марок — некритичные блоки с отдельной ошибкой.

**Отмена и повторная загрузка.** Каждая загрузка получает номер поколения и
собственную отмену: завершившийся позже старый запрос не заменяет текущую
карту, не сбрасывает её права и не выводит свою ошибку.

**Редактор.** Устранены nullable-геттеры `RowItem` (источник выбирается по
наличию локальной записи, а не по значению поля); новые записи подписываются
на изменения; выбор специального уровня помечает состояние; команда
сохранения передаёт нормализованный порядок; при переносе позиции под
родителя очищается собственный раздел.

**Версионные тесты.** Два падения `HKCardVersioningIntegrationTests` разобраны:
общий переключатель статуса утверждение отменён, поэтому тесты утверждают
карту назначенным согласующим через этапы. Расхождение ожидания теста с
доменом зафиксировано: утверждение новой версии само по себе не архивирует
предшественника — замена выполняется отдельной командой архивирования.
